## Завдання 2. Нова роль «auditor»

**Зміна політики** у [policies/rbac.yaml](policies/rbac.yaml). Ролі `auditor` дано лише одне право, `audit:read`:

```diff
@@ -14,3 +14,5 @@ roles:
     - "billing:read"
     - "audit:read"
     - "approvals:decide"
+  auditor:
+    - "audit:read"
```

**Випуск токена** роллю IdP (`security.py`). Токен підписується приватним ключем із `.keys/`, а шлюз перевіряє його публічним ключем:

```bash
source .venv/bin/activate
uvicorn platform_lite.gateway:app --port 8000      # окремий термінал; політика читається при старті

AUDITOR=$(python -c "from platform_lite import security as s; print(s.issue_token('ivan@telco.com','telco-crm','auditor'))")
CID=C1224                                          # клієнт орендаря telco-crm
```

**Три запити та їхні результати:**

```text
$ curl -s -w '\nHTTP %{http_code}\n' localhost:8000/v1/audit/customers/$CID -H "Authorization: Bearer $AUDITOR"
{"customer_id":"C1224","events":[]}
HTTP 200

$ curl -s -w '\nHTTP %{http_code}\n' -X POST localhost:8000/v1/models/churn-predictor/predict \
    -H "Authorization: Bearer $AUDITOR" -H "Content-Type: application/json" -d '{"customer_id":"C1224"}'
{"detail":"Role 'auditor' lacks scope 'models:invoke'"}
HTTP 403

$ curl -s -w '\nHTTP %{http_code}\n' localhost:8000/v1/billing/usage -H "Authorization: Bearer $AUDITOR"
{"detail":"Role 'auditor' lacks scope 'billing:read'"}
HTTP 403
```

**Висновок.** Аутентифікацію (401) auditor проходить, а авторизацію шлюз виконує за scope ролі з YAML:

- читати аудит дозволено;
- викликати модель і переглядати білінг заборонено, і в тексті 403 видно, якого саме scope бракує.

Нову роль додано без змін у коді, лише через політику в Git.

Під час виконання виникли дві проблеми:

- У першій версії ролі були ще `models:read`, `agents:read` і `billing:read`. Через це `/v1/billing/usage` повертав 200 замість 403, тому роль урізано до `audit:read`.
- Один із запитів повернув 401. У журналі аудиту для нього записано шлях `/v1/audit/customers/` і рішення `401: DecodeError`, тобто змінні `$AUDITOR` і `$CID` були порожні: їх задали в іншому терміналі. Змінні оболонки діють лише в тому терміналі, де їх створили.

## Завдання 3. Експеримент із guardrail

**Зміна** у [platform_lite/config.py](platform_lite/config.py):

```diff
-MAX_AUTO_DISCOUNT = 15          # % — вище потрібне схвалення людини (guardrail)
+MAX_AUTO_DISCOUNT = 10          # % — вище потрібне схвалення людини (guardrail)
```

**Запуск:** `python demo.py`. Усі самоперевірки пройшли: «Перевірок: 33, успішно: 33, невдало: 0».

**Сценарій 4.** Агент запропонував знижку 12%. Вона більша за новий ліміт 10%, тому guardrail відправив пропозицію на схвалення людині, і агент повернув статус `pending_approval`. Фрагмент виводу та trace (`request_id` і `approval_id` в кожному запуску свої):

```text
POST /v1/agents/retention-agent/invoke          → 200 ✅
     агент для клієнта C1200: status=pending_approval, offer=12% знижка лояльності + пріоритетна підтримка
```

```json
      {
        "tier": "agent",
        "op": "draft_offer",
        "latency_ms": 0.0,
        "discount_pct": 12
      },
      {
        "tier": "agent",
        "op": "guardrail_check",
        "latency_ms": 0.0,
        "needs_approval": true,
        "limit_pct": 10
      },
      {
        "tier": "agent",
        "op": "human_approval",
        "result": "pending",
        "approval_id": "apr_158db3"
      }
```

Коли ліміт був 15, ця сама знижка 12% проходила автоматично, і агент повертав статус `offer_sent`.

**Чому це зміна політики в коді (PR), а не в промпті.** Ліміт перевіряє вузол `guardrail_check` у коді агента (`offer["discount_pct"] > config.MAX_AUTO_DISCOUNT`). Тому модель не може його обійти, «переконати» чи забути, як могла б зробити з інструкцією в промпті, а її відповідь лише пропонує знижку, яку потім перевіряє детермінований код. Зміна ліміту з 15 на 10 змінює бізнес-ризик: визначає, які знижки йдуть клієнту автоматично, а які чекають схвалення людини. Тому таку зміну має бачити й погоджувати відповідальна особа, а не лише той, хто правив текст. PR дає це з коробки: diff у Git, рев'ю, CI-перевірки, автора й дату зміни, а за потреби простий відкат через revert. Зміну в промпті натомість не можна протестувати детерміновано й неможливо гарантувати.

## Завдання 4. Рефлексія

Найкориснішим для себе я вважаю розуміння того, що надійність LLM-застосунку залежить не лише від моделі, а й від платформи навколо неї. Під час роботи я побачив, як перевірка прав у шлюзі та роль `auditor` допомагають обмежувати доступ без змін у коді застосунку. Експеримент із `guardrail` також показав, чому важливі чіткі правила: знижка понад встановлений ліміт має чекати на схвалення людини, а не залежати лише від промпту. Ще один корисний висновок — `request_id` і журнал аудиту полегшують пошук причин і відстеження рішень. Для реального використання демо потрібно буде посилити захист журналу, винести ліміти й бюджети у спільне сховище та налаштувати керування ключами. Ці підходи я хотів би застосовувати у власних проєктах, бо вони роблять систему зрозумілішою, контрольованішою та безпечнішою.
